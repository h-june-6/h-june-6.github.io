> 개인 프로젝트를 진행하려면 두 서빙 엔진의 구조 차이를 확실히 알아야 해서 공부했다.

### 로컬 LLM이란

로컬 LLM은 OpenAI나 Anthropic 같은 외부 API를 호출하는 대신, 오픈 웨이트 모델을 내 컴퓨터나 서버의 GPU에 직접 올려 실행하는 방식이다. Llama, Qwen, Gemma처럼 가중치가 공개된 모델을 Hugging Face에서 내려받아 쓴다.

직접 돌리면 이런 점이 좋다.

- 데이터가 외부로 나가지 않는다. 사내 문서나 개인 정보를 다룰 때 중요하다.
- 호출량이 많으면 API 요금보다 자체 GPU를 쓰는 편이 유리할 수 있다.
- 모델을 골라 쓰고 미세 조정할 수 있으며 인터넷 없이도 동작한다.

대신 모델이 GPU 메모리(VRAM)에 올라가야 한다는 제약이 생긴다. 가중치 크기는 대략 파라미터 수에 파라미터당 바이트 수를 곱한 값이다. 예를 들어 70억 개 파라미터 모델을 16비트로 올리면 가중치만 약 14GB를 차지한다. 그래서 가중치를 4비트나 8비트로 줄이는 양자화(GGUF, AWQ, GPTQ 등)를 많이 쓴다.

개인 PC에서는 Ollama, LM Studio, llama.cpp 같은 도구로 쉽게 실행할 수 있다. 여러 사용자의 요청을 동시에 처리해야 하는 서버 환경에서는 vLLM, SGLang 같은 서빙 엔진을 쓴다.

### 서빙 엔진이란

모델 파일은 숫자 덩어리일 뿐이라서 그것만으로는 질문에 답하지 못한다. 가중치를 올리고 입력을 토큰으로 바꿔 연산하고 결과를 다시 글자로 되돌려 사용자에게 응답하는 소프트웨어가 필요하다. 이 역할을 하는 것이 추론 엔진이고 여러 요청을 효율적으로 처리해 서비스 형태로 제공하는 것이 서빙 엔진이다.

LLM의 추론은 두 단계로 나뉜다.

- **Prefill**: 입력 프롬프트 전체를 한 번에 처리해 첫 토큰을 만든다. 연산량이 많아 계산 성능이 중요하다.
- **Decode**: 토큰을 하나씩 이어서 생성한다. 한 번에 한 토큰만 만들기 때문에 매번 가중치와 KV 캐시를 메모리에서 읽어야 하고 메모리 대역폭이 병목이 된다.

서빙 엔진은 대략 이런 일을 한다.

- 여러 사용자의 요청을 받아 효율적으로 묶어서 처리한다(배칭과 스케줄링).
- GPU 메모리, 특히 KV 캐시를 관리한다.
- 토큰을 생성하고 샘플링한다.
- OpenAI API와 호환되는 HTTP 서버를 제공한다.

### LLM 서빙에서 풀어야 하는 문제

LLM은 토큰을 하나씩 생성하는데, 이때 이전 토큰들의 Key, Value 값을 매번 다시 계산하지 않도록 GPU 메모리에 저장해 둔다. 이것이 KV 캐시다. 이 캐시는 시퀀스가 길어질수록, 동시에 처리하는 요청이 많아질수록 커진다. 결국 한 GPU가 동시에 처리할 수 있는 요청 수는 연산 능력보다 KV 캐시가 차지하는 메모리에서 정해진다.

기존 방식은 요청마다 최대 길이만큼 연속된 메모리를 미리 잡아 두었다. 실제 생성 길이는 미리 알 수 없어서 쓰지 않는 공간이 생기고 요청마다 크기가 달라 단편화도 생겼다. 이 낭비를 줄이는 것이 서빙 엔진의 핵심 과제였다.

### vLLM

#### PagedAttention

vLLM은 운영체제의 가상 메모리 페이징에서 아이디어를 가져왔다. KV 캐시를 고정 크기 블록으로 나누고 블록이 물리 메모리에서 연속되지 않아도 되도록 블록 테이블로 논리 순서와 물리 위치를 연결했다. 필요한 만큼만 블록을 할당하므로 낭비가 줄고 같은 메모리에 더 많은 요청을 올릴 수 있다. 병렬 샘플링처럼 앞부분을 공유하는 경우에는 블록을 복사하지 않고 공유하다가, 내용이 달라지는 시점에 복사하는 copy-on-write 방식을 쓴다.

#### Continuous batching

요청을 묶어서 한 번에 처리하고 전부 끝날 때까지 기다리면, 먼저 끝난 요청의 자리가 낭비된다. vLLM은 토큰을 하나 생성하는 단계(iteration)마다 배치를 새로 구성한다. 끝난 요청은 바로 빼고 대기 중인 요청을 그 자리에 채워 GPU가 놀지 않게 했다.

#### Prefix caching

같은 시스템 프롬프트로 시작하는 요청이 많으면 앞부분의 KV 캐시를 다시 계산할 필요가 없다. vLLM은 블록 단위로 내용을 해시해 같은 블록이 이미 있으면 재사용한다. 재사용 단위가 블록이라서 접두사가 블록 경계에 맞지 않으면 그 뒤쪽 일부는 재사용하지 못한다.

### SGLang

#### RadixAttention

SGLang은 KV 캐시를 radix tree로 관리한다. 트리의 경로가 토큰 시퀀스이고 노드가 그 구간의 KV 캐시를 가리킨다. 새 요청이 들어오면 트리에서 가장 길게 일치하는 접두사를 찾아 그 부분은 재사용하고 나머지만 새로 계산한다. 일부만 일치하면 노드를 쪼개 공통 부분을 공유한다. 메모리가 부족하면 가장 오래 쓰이지 않은 말단 노드부터 제거한다. 공유 프롬프트, 다중 턴 대화, 같은 맥락에서 여러 갈래로 생성하는 작업처럼 접두사가 겹치는 상황에서 재사용이 자동으로 일어난다.

#### 캐시를 고려한 스케줄링

캐시 재사용률이 높은 요청을 먼저 처리하도록 스케줄링해 쓸모 있는 캐시가 제거되기 전에 활용한다. 캐시 구조와 스케줄러가 서로 맞물려 설계되었다는 점이 인상적이었다.

#### 프론트엔드 언어와 구조화된 출력

SGLang은 여러 번의 LLM 호출을 프로그램처럼 작성하는 프론트엔드 언어도 제공하고 JSON처럼 출력 형식을 제한하는 구조화된 출력을 효율적으로 처리하는 기능도 있다. 서빙 엔진이면서 LLM 프로그램을 짜기 위한 도구를 겸한다는 점이 vLLM과 다르다.

### 두 프레임워크 비교

| 구분 | vLLM | SGLang |
|---|---|---|
| 핵심 아이디어 | PagedAttention (블록 단위 관리) | RadixAttention (radix tree 관리) |
| 접두사 재사용 단위 | 블록 | 토큰 시퀀스 (트리 경로) |
| 캐시 탐색 구조 | 블록 해시 | 트리 접두사 매칭 |
| 스케줄링 | continuous batching | continuous batching + 캐시 고려 |
| 강점 | 메모리 효율, 범용성 | 접두사가 많이 겹치는 워크로드, 구조화된 출력 |

두 프레임워크는 서로의 장점을 빠르게 받아들이며 발전하고 있다. 위 표는 설계의 출발점을 비교한 것이고 실제 성능 차이는 버전과 워크로드에 따라 달라진다.

### 공부하며 느낀 점

KV 캐시를 어떻게 저장하고 공유하고 제거하느냐에 따라 같은 모델도 처리량이 크게 달라진다는 점을 가장 크게 배웠다. 한편 캐시를 공유하면 요청들이 같은 자료구조를 함께 쓰게 된다. 성능을 위한 설계가 신경 쓸 지점을 새로 만든다는 것도 알게 되었다.

### 다음 공부 계획

vLLM과 SGLang의 구조를 정리하며 서빙 엔진의 KV 캐시 관리가 성능뿐 아니라 안정성과도 직결된다는 점이 궁금해졌다. 이어서 아래 내용을 공부할 예정이다.

- **SGLang 내부 구조**: radix tree 기반 KV 캐시, 슬롯 인덱스 관리, 스케줄러, attention 커널의 동작을 코드로 직접 따라가 본다.
- **GPU 아키텍처와 커널 프로그래밍**: GPU 메모리 계층과 CUDA, Triton의 실행 모델을 익혀 attention 커널을 읽고 수정할 수 있도록 한다.
- **오류정정부호**: 패리티, 해밍 코드, SECDED의 원리와 GPU 메모리에서 일어나는 비트 오류(soft error, Rowhammer)를 공부한다.
- **보안 위협 모델과 실험 설계**: 공유 GPU 환경에서 공격자의 능력을 어떻게 가정하는지, 결함 주입 실험과 성능 평가(TTFT, TPOT, 처리량)를 어떻게 설계하는지 배운다.
