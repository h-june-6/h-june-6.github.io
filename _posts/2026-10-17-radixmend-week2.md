> RadixMend 2주차 기록. KV 헤드 벡터 하나(256바이트)를 15비트로 지키는 SECDED 코드를 만들고 설계대로 동작하는지 가능한 오류를 하나도 빼지 않고 확인했다.

## 이번 주에 하기로 한 것 (WBS)

- 결함 주입 도구 완성 (KV 텐서, 슬롯 인덱스)
- 무결함 기준선 측정 (출력, TPOT, TTFT, 처리량, 메모리)
- SECDED 참조 구현과 단위 테스트: 체크비트까지 포함한 전체 코드워드에서 단일 오류는 전부 교정, 이중 오류는 전부 탐지

기준선 측정은 GPU가 있어야 해서 아직 못 했다. 나머지 둘은 CPU로 끝냈다.

## 코드 구조 다시 보기

bf16 헤드 벡터는 128원소 × 16비트, 데이터 비트가 2048개다. 비트마다 (원소 번호 e, 원소 안 비트 위치 b) 라벨을 붙이고 체크워드는 이렇게 만든다.

| 필드 | 비트 수 | 뜻 |
|---|---|---|
| P | 1 | 데이터 전체 패리티 |
| S_e | 8 | 패리티가 홀수인 원소들의 e 라벨을 전부 XOR |
| S_b | 5 | 1인 데이터 비트들의 b 라벨을 전부 XOR |
| Q | 1 | 데이터 + P + S_e + S_b 전체 패리티 |

다 합치면 15비트라 int16 하나에 들어간다. KV 대비 메모리는 2/256, 0.78%다.

라벨은 0을 빼고 키로 섞은 비밀 순열에서 고른다. 0을 빼는 이유는 라벨이 0인 데이터 비트가 깨지면 P 비트가 깨진 것과 신드롬이 똑같아지기 때문이다. 순열은 BLAKE2b keyed 모드로 만들어서 키가 같으면 어느 기계에서 돌려도 같은 라벨이 나온다.

```python
from radixmend.secded_vec import VecCode

code = VecCode()                 # 128원소, E=8, B=5, 15비트
cw = code.encode(x)              # x: uint16[..., 128] (bf16을 비트 패턴으로 본 것)
x_fixed, cw_fixed, status, pos = code.decode(x_received, cw_received)
```

## 판정 규칙

읽을 때 신드롬 (ΔP, ΔS\_e, ΔS\_b, ΔQ)를 계산한다. ΔQ는 받은 코드워드 전체의 패리티다.

| 조건 | 판정 |
|---|---|
| 전부 0 | 정상 |
| ΔQ=1, ΔP=1, ΔS≠0, 두 라벨 다 실제로 쓰는 값 | 데이터 비트 (e, b) 오류 → 교정 |
| ΔQ=1, ΔP=1, ΔS=0 | P 비트 오류 |
| ΔQ=1, ΔP=0, ΔS가 비트 하나만 1 | S 비트 하나가 깨짐 |
| ΔQ=1, ΔP=0, ΔS=0 | Q 비트 오류 |
| ΔQ=0인데 신드롬이 0이 아님 | 2비트 오류 → 탐지 |
| 나머지 | 3비트 이상 → 탐지 |

체크비트가 깨진 경우엔 데이터는 그대로 두고 체크워드만 새로 쓴다. 15비트 신드롬은 2^15가지밖에 안 되니까 이 규칙을 전부에 적용해서 표로 만들어 뒀다. 커널에서는 같은 규칙을 분기 몇 개로 계산한다.

## "전부" 검증한 방법

이 코드는 GF(2)에서 선형이다. 그래서 어떤 오류든 신드롬은 뒤집힌 위치들의 패리티 검사 행렬 열을 XOR한 값이고 데이터가 뭐였는지와는 상관없다. 위치마다 열을 하나씩 구해 두면 오류 조합 하나를 XOR 몇 번으로 판정할 수 있다.

```python
cols = code.columns()                      # 위치 2063개의 신드롬
j, k = np.triu_indices(len(cols), 1)       # 2비트 조합 전부
assert (code.lut_status[cols[j] ^ cols[k]] == DETECTED).all()
```

데이터 2048비트에 체크비트 15비트를 더한 2063비트 전체에서 이만큼을 셌다.

- 단일 오류 2,063개
- 이중 오류 2,126,953개
- 삼중 오류 1,461,216,711개

## 결과

| 검사 | 결과 |
|---|---|
| 단일 오류 | 2,063개 전부 정확한 위치에서 교정 |
| 이중 오류 | 2,126,953개 전부 탐지 (잘못 고친 것 0, 정상으로 본 것 0) |
| 실제 bf16 데이터에 단일 오류 전부 | 6,189건 모두 원래 값과 체크워드로 복원 |
| 실제 데이터에 무작위 이중 오류 | 2,000건 전부 탐지 |
| popcount 방식 인코딩 vs 정의대로 인코딩 | 결과 같음 |

마지막 줄은 커널에서 쓸 계산법을 확인한 거다. S\_b의 k번째 비트는 "b 라벨의 k번째 비트가 1인 위치만 남기는 마스크 M\_k"를 쓰면 parity(Σ popcount(x\_i & M\_k))로 구할 수 있다. 원소마다 popcount 다섯 번이면 끝나서 GPU에서 싸다. 이 결과가 비트를 하나하나 도는 원래 정의와 똑같은지 비교했다.

코드워드를 2개, 4개로 나눈 경우(64원소, 32원소)도 똑같이 돌렸고 모두 통과했다.

## 예상 못 한 숫자 하나

삼중 오류는 원래 SECDED가 책임지는 범위가 아니다. 그래도 15억 개를 다 셀 수 있으니 세어 봤다.

| 라벨 | 3비트 오류가 조용히 잘못 고쳐지는 비율 |
|---|---|
| 순서대로 붙인 라벨 (1..128, 1..16) | 75.5% |
| 비밀 순열 라벨 | 27.1% (키 4개 평균) |

비밀 라벨은 원래 공격자가 원하는 대로 잘못 고치게 만드는 걸 막으려고 넣은 건데, 잘못 고쳐지는 비율 자체가 75%에서 27%로 뚝 떨어졌다. 이유는 라벨 공간에 빈자리가 생겨서다. 순서대로 붙이면 1~128, 1~16을 꽉 채워 쓰는데, 순열로 고르면 8비트 공간 255개 중 128개, 5비트 공간 31개 중 16개만 쓴다. 3비트 오류의 신드롬이 안 쓰는 라벨에 떨어지면 탐지로 끝난다. 대충 (128/255) × (16/31) ≈ 26%라서 측정값이랑 맞는다.

여기서 개선 아이디어가 하나 나왔는데 5주차 글에서 다룬다.

## 트러블슈팅

### 1. 전수 검증이 틀릴 수 있는 지점

**문제.** 전수 검증은 위치마다 신드롬 열을 계산해 두고 XOR하는 방식이다. 빠르긴 한데 열을 만드는 코드가 하나라도 틀리면 15억 건 결과가 전부 같이 틀린다. 게다가 이 경우엔 검증 결과가 "전부 통과"로 나와서 틀렸다는 걸 알아챌 방법이 없다. 특히 체크비트 열은 "자기 비트 + 전체 패리티 Q"로 만들어야 하고 Q 자신은 예외라서 실수하기 쉬운 자리였다.

**해결.** 열을 믿기 전에 열부터 검증했다. 실제 데이터에서 무작위 위치 200곳을 진짜로 뒤집고 디코더가 계산한 신드롬이 columns()가 준 열과 같은지 비교하는 테스트를 따로 만들었다. 실제 bf16 데이터로 단일 오류 6,189건을 처음부터 끝까지 encode/decode해 보는 검사도 같이 돌렸다. 두 방식이 서로 다른 경로로 같은 결론을 내야 전수 검증 결과를 믿을 수 있다.

### 2. 삼중 오류 15억 개를 어떻게 세나

**문제.** 위치 i < j < k 조합을 그대로 세 겹 반복문으로 돌리면 15억 번이다. 파이썬 반복문으로는 몇 시간이 걸린다.

**해결.** 2비트 조합 (j, k)의 신드롬을 np.triu\_indices 순서로 한 번만 만들어 둔다. 이 순서는 j 기준으로 정렬돼 있어서 "j > i인 쌍"이 배열의 뒷부분 한 덩어리가 된다. 그러면 i마다 그 뒷부분에 열 i를 XOR하고 판정표를 한 번에 조회하면 끝난다. 반복문은 i에 대해서만 2,061번 돌고 나머지는 numpy가 처리한다. CPU에서 약 12초 걸렸다.

```python
j, k = np.triu_indices(n, 1)                # j 기준 정렬
pair_syn = cols[j] ^ cols[k]
starts = np.searchsorted(j, np.arange(n), side="right")
for i in range(n - 2):
    s = pair_syn[starts[i]:] ^ cols[i]       # j > i인 쌍만
    counts += np.bincount(lut[s], minlength=4)
```
