KV 값 하나가 깨지는 것보다 KV를 가리키는 slot 번호가 깨지는 게 더 무섭다. 4주차 인덱스 실험(RQ1-5)에서 상위 비트가 뒤집히면 KV 풀 밖을 읽어 엔진이 죽었고, 하위 비트가 뒤집히면 다른 slot의 멀쩡한 KV를 읽어 아무 경고 없이 출력이 바뀌었다. 11주차에는 이 두 구조, 트리 노드의 `node.value`와 요청별 slot 표인 `req_to_token`에 SECDED를 넣었다.

## 코드는 먼저 만들어 뒀다

인코딩 자체는 순수 계산이라 GPU를 받기 전에 먼저 만들어 두었다. 32비트 데이터에 해밍 체크비트 6개와 전체 패리티 1비트를 붙인 확장 해밍 코드다. 교과서식으로 체크비트를 1, 2, 4, 8번째 자리에 끼워 넣으면 데이터 비트가 흩어져서 slot 번호를 쓸 때마다 다시 모아야 하니, systematic 형태로 바꿔 데이터는 아래쪽에 그대로 두고 체크비트를 위에 모았다. 이렇게 하면 `값 & 0xFFFFFFFF`가 곧 slot 번호다. 모든 값 왕복, 모든 비트 단일 플립 교정, 이중 플립 탐지를 전수로 확인해 두었다.

## 두 구조에 넣는 방법이 달랐다

`node.value`는 int64인데 slot 번호는 32비트면 충분하다. 그래서 32~38번 비트에 코드 7비트를 넣고, 39번 비트에 "인코딩된 값"이라는 표시를 하나 더 달았다. 표시가 있으면 검사하고, 없으면 평범한 값으로 읽는다. 표시 비트 자체가 뒤집히면 그 값은 평범한 값으로 읽히는데, 아래 32비트는 멀쩡하니 slot 번호는 맞게 나온다. 40번 이상 비트는 읽을 때 마스크로 지워 버린다.

`req_to_token`은 int32라 32비트 전부가 데이터다. 넣을 자리가 없다. 그래서 같은 모양의 int8 그림자 표를 따로 만들어 코드만 거기 넣었다. 표 크기는 원래의 4분의 1이다. `req_to_token`에 쓰는 함수 두 곳(`ReqToTokenPool.write`, `write_cache_indices`)을 감싸서 쓸 때마다 그림자 표도 같이 갱신하게 했다.

## 어디서 검사하나

쓰는 곳보다 읽는 곳 찾기가 어려웠다. 1주차 코드 분석 때 정리해 둔 목록을 다시 보면서, 모든 attention이 지나가는 길목을 찾았다. `req_to_token`에서 이번 batch의 slot 번호를 모아 `kv_indices`를 만드는 `pack_read_stream`이다. 여기 바로 뒤에 커널을 하나 더 붙여서, 방금 모은 값을 그림자 표와 같이 다시 읽어 1비트 오류면 `kv_indices`와 원래 표를 둘 다 고치게 했다. attention이 읽기 전에 고쳐지니 다른 slot을 읽을 틈이 없다.

`node.value`는 트리 경로를 모으는 `collect_full_device_indices`와 prefix match가 노드 값을 직접 모으는 `_match_prefix_helper`에서 검사한다. 고친 값은 노드에도 되쓴다. slot을 반납하는 `free`도 감싸서, 인코딩된 값이 섞여 들어오면 검사하고 표시를 떼어 넘긴다.

## 정확성은 바로 나왔다

4주차와 같은 설정으로 각 30회를 다시 돌렸다.

| 대상         | 비트                 | 무보호: 크래시 / 출력 변화 | 모듈 B: 크래시 / 출력 변화 | B가 교정   |
|--------------|----------------------|----------------------------|----------------------------|------------|
| node.value   | 하위                 | 0 / 29                     | 0 / 0                      | 30         |
| node.value   | 상위 (32 미만, 11회) | 11 / 0                     | 0 / 0                      | 11         |
| node.value   | 상위 (32 이상, 19회) | 0 / 0                      | 0 / 0                      | 체크비트 1 |
| req_to_token | 하위                 | 0 / 1                      | 0 / 0                      | 30         |
| req_to_token | 상위                 | 28 / 0                     | 0 / 0                      | 30         |

무보호 때 크래시 39번, 조용한 출력 변화 30번이 전부 사라졌다. 결함이 없을 때 결정적 모드 출력도 보호 없음, B만, 네 모듈 전부에서 똑같았다(golden `5c08f1c6447d`). 여기까지는 순조로웠다.

## TTFT가 두 배가 됐다

성능을 재 보니 TPOT은 c8 +2.6%, c32 +7.2%였는데 TTFT가 c8에서 323 ms에서 769 ms로, +138%였다. 네 모듈을 다 켜면 +83%였다. 정확성 실험만 보고 좋아할 뻔했다.

prefill 쪽인데 B가 하는 일은 노드 값 검사 정도라 이렇게 클 리가 없다고 생각했다. 코드를 다시 보니 의심 가는 데가 있었다. 검사를 torch 연산으로 짰는데, 패리티 하나 계산하는 데 시프트와 XOR가 여러 번이고 비트 위치마다 반복하니 노드 하나 검사하는 데 작은 연산이 60개쯤 나간다. 스케줄러는 대기 중인 요청마다 매 step prefix match를 부르니 그게 그대로 곱해진다.

그래서 프로파일보다 수정을 먼저 했다. 인코딩과 검사를 Triton 커널 하나로 합치고, 같은 step 안에서 같은 노드를 여러 번 match하면 검사는 처음 한 번만 하게 했다. 수정 전 코드의 프로파일은 그 뒤에 떴는데, 짐작이 맞았다. match 호출 횟수는 B가 있든 없든 같았는데 GPU 커널 launch 수가 3만 5천 개에서 68만 8천 개로 늘어 있었고, 거의 전부 torch의 원소별 연산이었다. 연산 하나하나는 빨라도 launch 비용이 쌓인 것이다. 수정본 재측정은 12주차로 넘어갔다.

## 아직 안 덮은 것

이번에 지킨 건 node.value와 req_to_token 두 가지다. 빈 slot 목록(`free_pages`)과 요청별 길이(`seq_lens`)는 아직이다. 빈 slot 목록이 깨지면 이미 다른 노드가 쓰는 slot을 새 요청에 내줄 수 있고, 길이가 깨지면 attention이 읽는 범위가 바뀐다. 12주차에 이어서 한다. 고칠 수 없는 2비트 인덱스 오류를 node.value와 req_to_token 사이에서 서로 복구하는 건 이번에도 못 했다.
