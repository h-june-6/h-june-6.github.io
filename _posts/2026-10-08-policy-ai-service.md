### 프로젝트 개요

2026 사회보장 AI 혁신 산학협력 프로젝트에서 4명이 한 팀(DGUF4)으로 참여해, 개정 법령을 자동으로 추적하고 AI로 분석해 주는 플랫폼을 개발했다. 협업 부서는 정보기획부였다. 나는 백엔드와 QA를 맡았다.

- **기간**: 2026.06 ~ 2026.09
- **팀 구성**: 4명 (팀장·DB, 백엔드, 프론트·AI 파이프라인, 백엔드·QA)
- **담당**: 백엔드 개발, 수집·분석 결과 검증(QA)
- **수상** : 우수상
- **기술 스택**: Python, FastAPI, PostgreSQL, HTML/JS, OpenAI API, 법제처 OpenAPI
- **GitHub**: <https://github.com/h-june-6/policy_ai_project>


### 해결하려던 문제

실무자는 국가법령정보센터에 수시로 접속해 관련 법령의 개정 여부를 직접 확인하고, 신구법 대비표를 열어 조문을 하나씩 대조해야 했다. 이 방식에는 세 가지 한계가 있었다.

- 사람이 확인하므로 개정을 누락하거나 늦게 알 수 있다.
- 조문 대조에 시간이 들고 해석이 사람마다 달라질 수 있다.
- 기존 정책 분석 플랫폼은 우리 업무에 맞는 기능을 제공하지 않았다.

그래서 **AI가 개정 전·후 조문을 조문 단위로 비교하고 요약해서, 실무자가 수작업 대조 없이 변경 내용과 업무 영향을 바로 파악하게 하는 것**을 목표로 잡았다. 같은 조문을 반복 분석하지 않도록 캐시 구조를 두어 지속적으로 운영할 수 있게 하는 것도 목표에 포함했다.

### 시스템 구조

법제처 OpenAPI로 현행 법령과 개정 전·후 조문 원문을 수집해 PostgreSQL에 저장하고, 매일 프로그램이 재조회해 개정된 법령만 교체한다. 법령 수집은 직접 개발한 파서를 거쳐 **3단계**로 처리했다.

1. **MST 대조**: 법령일련번호(MST)를 DB와 비교해 바뀐 법령만 전문을 다시 받는다.
2. **Node-Diff 정밀 판별 엔진**: 조·항·호·목을 노드로 쪼개 직전 판본과 비교해 실제로 바뀐 조항만 뽑는다.
3. **분리시행 사각지대 추적 큐**: 조문마다 시행일이 다른 개정은 새 MST가 발급되지 않아 대조로 잡히지 않는다. 시행일이 도래하면 강제로 재조회하도록 대기 큐에 넣었다.

바뀐 조문은 OpenAI 모델이 분석해 변경 요약, 실무 영향, 조치 사항, 적용 시점으로 정리하고, 결과는 웹 화면과 마크다운, PDF, 한글(hwpx) 리포트로 제공한다. 사용자는 부서별 계정으로 로그인해 자기 부서의 감시 법령만 본다.

### 기술적으로 고민한 지점

#### 1. 법제처 응답을 조항호목 노드로 파싱했다

법제처 API 응답은 형식이 일정하지 않았다. 목이 항 바로 아래에 오기도 하고 호 안에 중첩되어 오기도 했으며, 같은 조문이 판본마다 다른 모양으로 오기도 했다. 호번호 필드에는 '1.'로 오지만 실제 번호는 본문 첫머리에 '1의2.'로 들어 있는 경우도 있었다.

- 조·항·호·목을 좌표로 바꿔 판본 간 비교의 기준으로 삼았다.
- 목이 어느 호에 속하는지 API가 알려 주지 않을 때는 법률 문장의 작성 관행을 이용했다. "다음 각 목의…"처럼 목을 예고하는 **앵커 문구**가 있는 호가 정확히 하나일 때만 그 호에 귀속시켰다. 불확실하면 틀린 호에 붙이지 않고 항 직속으로 두고 inferred 플래그를 세웠다. 틀린 번호를 보여 주는 것보다 생략하는 편이 낫다고 판단했다.
- 호 귀속 정보만 채워진 경우는 조문 이동이 아닌 같은 조항으로 처리했다. 이 처리가 없으면 법에는 변화가 없는데도 조문 수십 개가 옮겨 다닌 것처럼 보였다.
- 원본 API 응답을 gzip으로 보관해, 파서를 개선한 뒤 저장된 원본으로 DB를 다시 만들 수 있게 했다. 현행법령 API는 과거 판본을 주지 않기 때문이다.

#### 2. 개정 감지의 사각지대를 메웠다

- 분리시행일을 파싱해 대기 큐에 넣고, 시행일이 도래하면 판본 번호가 그대로여도 재조회한다. 법제처 갱신이 늦을 수 있어 최대 7회 재시도하고, 그래도 변화가 없으면 실패로 기록한다.
- 점검 결과를 로그 테이블에 남겨 '개정이 없어서 조용한 것'과 'API 장애로 조용한 것'을 구분했다.
- 점검을 멱등하게 만들어 서버가 꺼져 있었더라도 켜질 때 한 번 돌리면 밀린 개정을 따라잡는다. 처음 수집한 법령은 비교 대상이 없으므로 개정으로 기록하지 않아, 최초 적재 때 가짜 개정이 쌓이는 문제를 막았다.

#### 3. LLM 분석의 누락과 비용을 구조로 해결했다

- 개정 폭이 커서 입력 상한을 넘으면 앞에서 자르는 대신, 조문번호와 제목 목록만 먼저 보내 영향 조문을 고르게 하는 **2단 스크리닝**을 적용했다. 뒤쪽 조문이 통째로 빠지는 일이 구조적으로 생기지 않는다.
- 분석 범위(전체, 선별, 부분)를 결과에 기록하고, 부분 분석이면 신뢰도를 자동으로 낮췄다.
- 입력, 부칙, 프롬프트 버전, 모델명을 합친 해시로 결과를 캐시했다. 같은 입력의 재분석 비용을 줄이면서, 프롬프트나 모델을 바꾸면 옛 결과가 재사용되지 않는다.
- LLM이 꺼져 있거나 호출이 실패하면 규칙 기반 분석으로 대체하고, 리포트에 AI 미사용으로 표시한다.

#### 4. 업로드 문서의 인용 법령을 탐지하고 현행과 대조했다

실무 문서(hwp, hwpx, pdf, docx 등)를 올리면 인용된 법령을 자동으로 찾아 개정 여부를 확인해 주는 기능이다.

- 한국어는 조사가 법령명 안팎에 모두 나와 이름의 시작 경계를 정하기 어렵다. 후보를 여러 개 만들고 법제처 조회로 현행에 실제 존재하는 이름을 골랐다.
- '동법 시행령 제76조', '제3조 및 제5조'처럼 앞 법령을 이어받는 표현은 선행사를 따로 관리했다.
- 판정은 법령명(정상, 개명 의심, 확인 필요)과 조문(개정됨, 신설, 삭제, 조항 없음) 두 축으로 나눴다.

#### 5. 부서별 권한과 보안을 설계했다

- 모든 경로를 기본 거부로 두고 공개 경로만 허용했고, 전사 관리자, 부서 관리자, 일반 사용자 3등급을 두었다.
- 비밀번호는 scrypt로 해시하고 세션 토큰은 해시만 DB에 저장했다.
- 한 부서가 법령을 삭제해도 다른 부서의 수집이 끊기지 않도록 구독 구조로 설계했다.

### 기대 효과와 확장 가능성

- 수시로 접속해 개정을 확인하던 수동 모니터링을 자동 탐지 체계로 바꿔 행정 지연과 법적 리스크를 줄일 수 있다.
- 사업계획서, 제안서, 지침서를 올리기만 하면 인용 법령의 개정 여부를 확인할 수 있어, 신규 사업 기획 단계에서 법적 리스크를 미리 점검할 수 있다.
- 법제처 API 기반이라 특정 부처에 한정되지 않고, 소관 법령이 있는 다른 기관에도 같은 방식으로 적용할 수 있다.

### 배운 점

- 외부 API 응답은 문서화된 형식과 다르다는 전제로 설계해야 했다. 파서가 판단하지 못하는 부분은 추측하지 않고 표시로 남기는 편이 시스템 전체의 신뢰도를 지켰다.
- AI 분석에서는 정확도만큼 결과가 어디까지 보고 낸 것인지를 사용자에게 알리는 일이 중요했다.
- 자동화 시스템에서는 '아무 일도 없었다'와 '확인하지 못했다'를 구분해 기록해야 운영 단계에서 문제를 찾을 수 있다.
- 실무자와의 소통이 가장 중요한 것 같다. 해당 프로젝트를 진행하면서 실무자 분과 미팅을 가질 때마다 우리의 방향성이 크게 크게 바뀌었던 걸 생각하면 갈피를 잡는데 소통이 중요한 것 같다. 좋은 소통 하나로 며칠을 세이브할 수 있다.
- UI가 중요한 것 같다. 우리는 맨날 우리의 프로그램을 들여다보고 있으니  프로그램이 직관적이고 편하다고 착각할 수 있다. 아예 처음 보는 사람의 입장에서는 또 다르다.

### 한계와 앞으로의 개선 방향

- 현재는 감시 대상 법령 자체의 개정만 감지한다. 하지만 법령은 서로 인용하고 위임하는 경우가 많아, 연계된 법령이 개정되어도 영향을 놓칠 수 있다는 것을 확인했다. 연계 법령이 개정될 때도 감지되도록 법령 간 관계를 반영하는 것이 다음 개선 과제다.
- 로그인과 세션 관리를 사회보장정보원 사내 서비스에 그대로 이식하기는 어렵다. 우리 팀은 기관 소속이 아닌 외부 참여자라서 사내 인증 체계에 연동해 개발하고 검증할 수 없었기 때문이다. 현재는 자체 구현한 부서별 계정과 세션으로 동작하므로, 실제 이식 단계에서는 기관의 인증 체계(SSO 등)에 맞춰 연동하는 작업이 필요하다.
